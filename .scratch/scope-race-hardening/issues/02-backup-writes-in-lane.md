# 02 — 백업 네임스페이스 쓰기를 레인 안으로

**What to build:** 백업 히스토리에서 두 행을 빠르게 연달아 지워도 **둘 다** 지워지고, 목록에
남은 행은 전부 실제로 복원된다. 지금은 각 삭제가 목록 전체를 다시 쓰기 때문에 겹치면 나중
것이 앞 것의 결과를 지우고, **목록에는 남아 있는데 실제 데이터는 없는 행**이 만들어진다.
사용자가 그 행으로 복원을 시도하면 '손상됨'을 만나고, 지운 적 없는 백업이 사라진 것으로 보인다.
이 티켓이 릴리스 r3의 R-3 중 서비스워커 쪽 절반을 닫는다.

01이 세운 Writer Lane에 자동 Backup·스냅샷 삭제·전체 초기화의 백업 정리를 태운다. 레인이
흡수하는 임시 조율 장치는 걷어내되, 직렬화가 아닌 **예약 정책**은 그대로 남긴다 — 그 구분이
`.scratch/scope-race-hardening/spec.md`의 D8이다.

**Blocked by:** 01 — Writer Lane 도입과 마이그레이션 직렬화.

**Status:** ready-for-agent

- [ ] 백업 네임스페이스를 고치는 모든 서비스워커 경로가 레인을 잡는다: 자동 Backup 발화 ·
      스냅샷 한 행 삭제 · 전체 초기화의 백업 비우기.
- [ ] 겹친 두 삭제가 **둘 다** 완료되고, 어느 쪽도 다른 쪽의 결과를 되살리거나 지우지 않는다.
- [ ] 매니페스트에 남은 항목은 전부 실제 데이터가 있다 — 삭제가 겹친 뒤에도.
- [ ] 지우지 않은 스냅샷은 삭제에 휩쓸리지 않는다.
- [ ] 삭제와 자동 Backup이 겹쳐도 결과가 정합하다 — 둘 중 하나가 다른 하나의 결과를 지우지 않는다.
- [ ] 레인이 흡수하는 장치가 제거된다: 진행 중 백업을 기다리는 드레인 await, 자동 Backup
      본문의 이중 중단 검사, 겹친 삭제끼리 방벽이 없던 자리.
- [ ] **예약 정책은 남는다** — 취소할 수 없는 타이머를 무효화하는 세대 번호, 그리고 초기화가
      끝까지 갔을 때만 곧바로 다시 예약하는 계약. 실패한 초기화 직후에 자동 Backup이 옛
      Profile을 다시 스냅샷하지 않는다(순서대로 돌아도 이 문제는 직렬화가 풀지 않는다).
- [ ] 전체 초기화가 끝까지 가면 곧바로 깨끗한 기본 상태의 스냅샷이 잡힌다.
- [ ] 이미 지운 행을 다시 지워도 오류가 나지 않는다(멱등).
- [ ] 백업 저장소 테스트의 픽스처 빌더에 **반환 타입을 명시**한다. 지금 그 빌더는 매니페스트
      항목이 요구하는 필드 이름과 다른 객체를 만들고 있고, 그래서 매니페스트가 빈 목록으로
      읽혀 **삭제가 매니페스트를 쓰는 분기가 한 번도 실행되지 않았다.** 반환 타입을 붙이면
      이 상태가 타입 검사에서 막힌다.
- [ ] 백업 저장소의 삭제 ↔ 자동 Backup 경합 테스트가 **삭제가 아니라 S3로 이동**된다. 티켓
      저널에 옮긴 단언을 원래 위치와 행 단위로 대응시켜 적고, 무효 픽스처였다는 사실 —
      즉 교체가 약화가 아니라 강화라는 것 — 을 근거와 함께 기록한다.
- [ ] 경합과 무관한 단위 테스트(삭제의 멱등성, 검증 실패 보고)는 원래 자리에 남는다.
- [ ] S3가 이 티켓 범위에서 확인하는 조합: 스냅샷 삭제 ↔ 스냅샷 삭제, 스냅샷 삭제 ↔ 자동
      Backup, 전체 초기화 ↔ 나머지 전부.
- [ ] 전 게이트 green — 타입 검사 · 단위 · 빌드 · 번들 · 스모크.
