# 02 — 백업 네임스페이스 쓰기를 레인 안으로

**What to build:** 백업 히스토리에서 두 행을 빠르게 연달아 지워도 **둘 다** 지워지고, 목록에
남은 행은 전부 실제로 복원된다. 지금은 각 삭제가 목록 전체를 다시 쓰기 때문에 겹치면 나중
것이 앞 것의 결과를 지우고, **목록에는 남아 있는데 실제 데이터는 없는 행**이 만들어진다.
사용자가 그 행으로 복원을 시도하면 '손상됨'을 만나고, 지운 적 없는 백업이 사라진 것으로 보인다.
이 티켓이 릴리스 r3의 R-3 중 서비스워커 쪽 절반을 닫는다.

01이 세운 Writer Lane에 자동 Backup·스냅샷 삭제·전체 초기화의 백업 정리를 태운다. 레인이
흡수하는 임시 조율 장치는 걷어내되, 직렬화가 아닌 **예약 정책**은 그대로 남긴다 — 그 구분이
`.scratch/scope-race-hardening/spec.md`의 D8이다.

**Blocked by:** 01 — Writer Lane 도입과 마이그레이션 직렬화.

**Status:** done

      스냅샷 한 행 삭제 · 전체 초기화의 백업 비우기.

      끝까지 갔을 때만 곧바로 다시 예약하는 계약. 실패한 초기화 직후에 자동 Backup이 옛

- [x] 전체 초기화가 끝까지 가면 곧바로 깨끗한 기본 상태의 스냅샷이 잡힌다.

- [x] S3가 이 티켓 범위에서 확인하는 조합: 스냅샷 삭제 ↔ 스냅샷 삭제, 스냅샷 삭제 ↔ 자동

### 구현 저널 (2026-07-30)

**`bk:` 쓰기가 모두 쓰기 문을 지난다.** 문에 두 매소드가 늘었다 — `snapshot()`(자동 Backup;
권위 상태를 스스로 읽어 payload·대상을 만든다)과 `deleteSnapshot(id, target)`. `backupStore`의
변이 함수 넷(`performBackup`·`deleteBackupSnapshot`·`applyBackupPlan`·`removeBackupKeys`)이
허가를 요구하고, 문이 **직수입**한다. `BackgroundDeps`에서 `performBackup`·
`deleteBackupSnapshot`·`readState`가 빠졌다 — 티켓 01의 structure r2가 가르쳐 준 "주입된 dep은
fan-out 자리"를 선제 적용한 것이다.

**레인이 흡수한 것 / 남긴 것** (D8의 구분)

| 걷어낸 것 | 왜 |
|---|---|
| 중단 깊이 카운터 | 겹친 작업이 서로의 창을 열 수 없다 |
| 진행 중 백업 드레인 await | 백업이 레인 작업이라 삭제와 겹칠 수 없다 |
| 자동 Backup 본문의 이중 중단 검사 | 위와 같음 |
| 삭제의 suspend/resume 전체 | 방벽이 레인이 됐으니 예약에 손댈 이유가 없다 |

| 남긴 것 | 왜 |
|---|---|
| 예약 세대 번호 | `setTimer`는 취소할 수 없다 |
| 초기화 `{snapshot}` 재예약 계약 | 실패 경로의 상태는 아직 옛 Profile — 직렬화가 풀지 못한다 |

**이중 검사를 걷어내며 새로 막은 창 둘.** 이 티켓의 가장 중요한 내용이다.

1. **요청 enqueue와 작업 본문 시작 사이.** 초기화 요청이 레인에 선 뒤 본문이 시작되기까지의
   사이에 발화한 타이머는 아직 옛 세대를 보고 스냅샷을 레인에 세운다 — 그 스냅샷은 초기화
   **뒤**에 돌고, 초기화가 reset-state에서 실패했다면 옛 Profile을 되살린다. 무효화를 그 창
   **앞**(요청 경계)으로 옮겼다.
2. **초기화 도중 걸린 예약** (코드리뷰가 찾은 것). 1의 무효화 뒤에 걸린 예약은 새 세대를 들고
   있어 세대 검사를 통과한다. 그래서 문이 **완료된 초기화 횟수**를 세고, 요청 시점보다 값이
   달라진 스냅샷은 쓰지 않는다. 부트스트랩의 세대와 겹치지 않는다 — 그쪽은 아직 발화하지 않은
   **타이머**를 무효화하고, 이쪽은 이미 요청된 **작업**의 착지를 막는다.

둘 다 변이로 red를 확인했다(경계 무효화 제거 → red / epoch 검사 제거 → red).

**R-3의 근본 원인을 실측했다.** `backupStore.test.ts`의 옛 픽스처
`{ id, at, profileCount, chunkCount, bytes }`는 `ManifestEntry`의 `createdAt`·`checksum`을
빠뜨린다. 직접 돌려 확인: `readManifest` → **0개**, `planSnapshotDelete.found = false`. 즉
**삭제가 매니페스트를 쓰는 분기가 한 번도 실행되지 않았다.** 두 테스트는 green이었지만 자기가
검증한다고 적은 분기에 도달하지 못했다. 새 픽스처 빌더 둘은 반환 타입 `: ManifestEntry`를 달아
그 상태가 타입 검사에서 막힌다.

**옮긴 단언 — 원래 위치와 행 단위 대응.** 넷 전부 삭제가 아니라 이동이고, 옮겨 간 자리는 S3다.

| 원래 위치 | 원래 이름 | 옮겨 간 곳 |
|---|---|---|
| `platform/backupStore.test.ts:126` | 읽기와 쓰기 사이에 커밋된 스냅샷이 사라지면 성공으로 접지 않는다 | S3 `삭제와 자동 Backup이 겹쳐도 결과가 정합하다` — 정방향(`{ok:true}`)과 역방향(고아 청크 0) 둘 다 |

| `runtime/background-bootstrap.test.ts:337` | 삭제는 진행 중인 자동 Backup을 드레인한 뒤에야 매니페스트를 읽는다 | S3 `삭제와 자동 Backup이 겹쳐도 결과가 정합하다` (드레인이 아니라 레인이 순서를 만든다) |

**이동이 약화가 아닌 근거**: 옛 두 어댑터 테스트는 위 실측대로 검증하려던 분기에 도달하지
못했다. 옛 두 부트스트랩 테스트는 겨누던 기계(드레인·깊이 카운터)가 사라졌고, 성질 자체는
S3가 진짜 어댑터와 유효한 픽스처로, 한 순서가 아니라 **모든 순서**에서 본다.

**삭제한 것 하나 — 릴리스 r2의 R-11 테스트** (`요구가 엇갈린 겹침에서도 삭제의 재예약은
살아남는다`). 그 결함은 정책 참여자가 둘일 때만 성립했다(삭제는 재예약을 무조건 요구, 초기화는
성공 때만). 삭제가 예약에 손대지 않게 되어 요구가 엇갈릴 상대가 없다. 초기화 둘이 겹치는
경우의 동작은 옛 코드와 **같다** — 첫 초기화가 요구를 소비한 뒤 둘째의 무효화가 그 예약을
누르고, 둘째가 실패하면 예약 없이 다음 상태 변경을 기다린다. 회귀가 아니라 같은 계약이다.

**원래 자리에 남긴 것 · 되살린 것.** 클라우드 삭제 셋(경합이 아니라 remove → 재조회 → 검증
경로)은 그대로 남았다. 그리고 코드리뷰가 잡은 것: 옮기면서
`verifySnapshotDeleteComplete`가 저장소 전체에서 **커버리지 0**이 됐다. 스펙이 "검증 실패
보고는 원래 자리에 남는다"고 적었으므로 어댑터 시임에 셋을 되살렸다 — remove가 청크를 남길 때
잔여 보고, 읽기 전부터 있던 고아 청크는 실패 근거가 아님, 저장소가 던지면 사유와 함께 실패.

### `/code-review` 처분 (2026-07-30)

고정점 `167fd14`. 두 축이 낸 지적 대부분을 수용했다. **셋은 제가 만든 실제 결함이었다.**

1. **`SnapshotOutcome`이 `too-large`를 '썼다'로 보고했다** (standards). `performBackup`은
   `plan.kind`를 그대로 돌려주고 거기에는 `'too-large'`가 있다 — quota로 아무것도 못 쓴 실행이
   `{status:'written'}`이 되어 로그에도 남지 않았다. 세 갈래로 갈랐다:
   `written` / `unchanged`(내용 동일, 정상) / `skipped`(읽을 수 없음 **또는 예산 초과**).
2. **겹침 테스트가 빈 타이머 목록을 터뜨렸다** (spec). 부트스트랩의 초기 예약은 마이그레이션
   커밋이 정착한 뒤 걸리므로 `start`에서는 목록이 비어 있다. 형제 테스트에서 이미 고쳤던
   실수를 여기서 반복했다. `stateChanged()`로 예약을 실제로 걸고, 단언도 정방향(`{ok:true}`)과
   역방향(고아 청크 0)으로 넓혔다 — 옛 테스트는 양쪽을 단언했는데 새 것이 어느 쪽도 안 봤다.
3. **`verifySnapshotDeleteComplete` 커버리지 0** (spec). 위 '되살린 것' 참조.
4. **잔여 창** (spec, low) — 초기화 도중 걸린 예약. 위 '새로 막은 창 둘'의 2번으로 닫았다.
5. 스테일 주석 셋(`stateStore`의 '중단·드레인', 부트스트랩 테스트 헤더, 게이트 주석이
