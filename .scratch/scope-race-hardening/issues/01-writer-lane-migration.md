# 01 — Writer Lane 도입과 마이그레이션 직렬화

**What to build:** 확장을 새 버전으로 올린 직후에 Profile을 켜거나 Modification을 고쳐도 그
편집이 남는다. 지금은 서비스워커가 깨어나며 도는 Schema Version 마이그레이션 커밋과 사용자
편집이 겹칠 수 있고, 마지막에 남는 것이 방금 한 편집이 아니라 올리기 전의 옛 스냅샷일 수 있다.
사용자에게는 "방금 켠 프로필이 저절로 꺼졌다"로 보인다. 이 티켓이 릴리스 r3의 R-2를 닫는다.

이 티켓은 나머지 다섯이 전부 올라탈 **Writer Lane**을 세운다 — 영속 저장소를 고치는 단 하나의
줄, 컴포지션 루트에서 한 번 만들어지고 화면은 얻을 수 없는 것. 그리고 그 줄이 실제로 배선됐음을
증명하는 통합 시임(S3)도 여기서 만든다. 설계 근거는 `docs/adr/0016-single-writer-lane.md`,
계약과 시임 정의는 `.scratch/scope-race-hardening/spec.md`의 D2·D3·D4·D5와 Testing Decisions에 있다.

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [x] Writer Lane이 컴포지션 루트에서 **한 번만** 만들어진다. 화면(팝업·탭)에서는 레인을 얻을
      방법이 없다 — 모듈 최상단 변수가 아니라 주입된 인스턴스여야 한다.
- [x] 레인 획득이 **타입으로 강제**된다. 레인 안에서만 불려야 하는 쓰기 함수를 레인 밖에서
      부르면 타입 검사가 실패한다. 이 성질을 확인하는 방법이 티켓 저널에 기록돼 있다.
- [x] 권위 상태를 쓰는 **모든** 진입점이 레인을 잡는다: 전이 명령 수신 · 전역 Pause 토글 ·
      만료 알람 · 재조정 중 발견된 지난 만료 · 전체 초기화 · 부트스트랩 마이그레이션 커밋.
      뒤의 넷은 명령 채널을 거치지 않고 실행자를 직접 부르던 경로다.
- [x] 안쪽 어댑터는 레인을 잡지 않는다. 전체 초기화가 내부에서 실행자를 다시 불러도 교착하지
      않는다.
- [x] 마이그레이션 커밋의 **읽기부터 커밋까지가 한 번의 획득 안에서** 돈다. 읽고 나서 놓았다가
      쓰기에서 다시 잡지 않는다.
- [x] 마이그레이션과 전이 명령이 **양방향 순서 모두** 정의된 결과를 낸다 — 명령이 먼저면 커밋이
      "할 일 없음"으로 물러나고, 마이그레이션이 먼저면 명령이 올라간 상태 위에서 계산된다.
      어느 쪽에서도 사용자 편집이 사라지지 않는다.
- [x] 명령 실행자의 자체 FIFO(tail 체인)가 제거된다. 같은 성질을 보장하는 기계가 둘 남지 않는다.
- [x] 실행자의 lost-update 테스트가 **삭제가 아니라 이동**된다 — 레인 층위에서 같은 성질을
      단언한다. 티켓 저널에 옮긴 단언을 **원래 위치와 행 단위로 대응**시켜 적는다.
- [x] 마이그레이션 커밋의 compare-and-swap 술어가 제거된다. 다만 저장소가 이미 새 버전이라
      굳힐 것이 없을 때 아무것도 쓰지 않는 경로와, 이 버전이 읽을 수 없는 상태 위에 쓰기를
      거부하는 Blocked 계약은 **그대로 남는다**.
- [x] 레인의 실패 계약 둘이 성립한다: 각 호출자는 자기 실패를 받고(다른 조작이 남의 오류를
      대신 받지 않는다), 레인은 언제나 전진한다(한 작업이 거부·throw해도 다음 작업이 실행되어
      저장까지 끝난다).
- [x] 거부-후-전진 테스트의 입력이 **설계된 거부 경로**다 — 이 버전이 읽을 수 없는 상태 위에
      쓰라는 요청. 지어낸 오류를 던지지 않는다.
- [x] **S3 통합 시임이 존재한다**: 배경 부트스트랩을 진짜 저장소 어댑터로 배선하고, 그 밑에
      모든 읽기·쓰기를 세울 수 있는 제어형 저장소 fake를 깐다. 결정론적 스케줄러가 보류 중인
      작업들의 **가능한 모든 순서를 열거**하고, 각 순서마다 불변식을 단언한다.
- [x] S3가 이 티켓 범위에서 확인하는 조합: 마이그레이션 커밋 ↔ 전이 명령(양방향), 전이 명령 ↔
      전이 명령, 그리고 위 여섯 진입점을 **각각** 다른 상태 쓰기와 겹쳐 세운 경우.
- [x] 불변식: 어떤 순서에서도 두 read-modify-write가 겹치지 않는다 · 겹쳐 도착한 전이가 전부
      최종 상태에 남는다 · 이 버전이 읽을 수 없는 상태 위에는 아무것도 쓰이지 않는다.
- [x] 테스트 픽스처 빌더에 **반환 타입을 명시**한다(이 티켓이 만지는 것에 한해). 필드 이름이
      틀린 픽스처가 타입 검사를 통과하지 못한다.
- [x] 전 게이트 green — 타입 검사 · 단위 · 빌드 · 스모크 · **writer-lane 게이트(신설)**.
      **번들 게이트는 티켓 07로 분리한다**
      — 이 티켓과 무관한 선재 실패이고(`1b7ddd8`에서 바이트 단위로 같은 수치), 초과분은 이
      게이트의 사다리 관례대로 실측·재트리아지가 필요한 별건이다 (사용자 결정 2026-07-30).

### 구현 저널 (2026-07-29)

**레인이 사는 곳.** `src/core/writer-lane.ts`. `runtime`이 아니라 `core`인 이유는 층 방향
때문이다 — 저장소에 실제로 쓰는 어댑터(`platform/stateStore`)가 증표를 **요구**해야 화면이
writer가 될 길이 타입으로 막히는데, `platform`은 `runtime`을 import하지 않는다(현 저장소의
방향: `entrypoints → {platform, runtime} → core`). 증표를 요구하는 쪽과 만드는 쪽이 함께
이름 부를 수 있는 층은 `core`뿐이다. 레인 자체는 promise 사슬 하나라 브라우저 API도 타이머도
만지지 않는다. **만드는** 것은 여전히 컴포지션 루트(`bootstrap`)가 한 번만 한다.

**타입 강제를 확인하는 법.** `src/runtime/service-worker.integration.test.ts` 맨 아래
`_laneAcquisitionIsTypeEnforced()` — 실행되지 않고 `tsc`만 읽는 블록이다. 세 줄의
`@ts-expect-error`가 각각 (1) 증표 없는 `persistState`, (2) 지어낸 객체를 증표 자리에 넣은
`persistState`, (3) 증표 없는 `commitMigration`을 막는다. 레인 밖 호출이 언젠가 유효해지면
그 `@ts-expect-error`가 쓸모없어져 **`bun run check`가 실패한다.** 즉 이 성질은 주석이 아니라
게이트다. 직접 보려면 그 파일에서 `@ts-expect-error` 한 줄을 지우고 `bun run check`를 돌리면
`TS2554: Expected 2 arguments, but got 1`이 그 자리에서 난다.

**옮긴 단언 — 원래 위치와 행 단위 대응.** 다섯 건 전부 삭제가 아니라 이동이고, 옮겨 간

### `/code-review` 처분 (2026-07-29)

고정점 `1b7ddd8`. 두 축 모두에서 나온 지적 여덟 건 중 여섯을 고쳤다.

**고침 — 실제 결함**

1. **화면이 자기 레인을 만들 수 있었다** (spec 축, 가장 큰 건). `persistState`는 증표를
   요구하지만 `createWriterLane`은 평범한 export라, 팝업 코드가
   `createWriterLane().run(h => persistState(h, s))`를 쓰면 타입 검사를 통과한다 — 컨텍스트마다
   락이 하나씩 생기는, ADR 0016이 물린 바로 그 모양이다. 타입 하나로는 못 닫는다.
   `src/runtime/renderer-boundary.test.ts`를 세워 **화면 entrypoint의 정적 import 그래프가
   레인 모듈에 닿지 않음**을 못 박았다(행동 시임이 아니라 번들 게이트와 같은 구조 게이트다).
   `import type`은 `verbatimModuleSyntax` 아래 지워지므로 간선으로 세지 않는다 — 저장소
   어댑터가 증표 **타입**만 가져오는 것은 화면을 레인에 잇지 않는다. 워커 entrypoint는
   반대로 **닿아야** 한다는 양성 대조를 함께 둬서 걷기가 실제로 본다는 것을 증명한다.
   변이 확인: `app.tsx`에 레인 import를 넣으면 두 건 red.
   ※ WXT가 `src/entrypoints/`의 모든 파일을 entrypoint로 스캔해 `wxt build`를 깨뜨리므로
   이 파일은 `src/runtime/`에 둔다(처음에 `entrypoints/`에 뒀다가 빌드가 잡았다).
2. **불변식 (a)가 여섯 진입점 중 셋에만 걸려 있었다.** 수용 기준 2는 "각각"을 요구한다.
   마이그레이션 양방향 둘에 `noLostEdits`를 걸었다 — 그 순서에서 커밋이 뒤에 쓰면 사용자
   편집을 지우므로, 옛 CAS가 막던 그 결함을 쓰는 순간 잡는다. 전체 초기화는 설계상 편집을
   지우므로 이 잣대를 댈 수 없고, 그 이유를 헬퍼 주석과 시나리오에 적었다.
   ※ 이 잣대를 `명령은 도착 순서대로 적용된다`에도 걸었다가 red가 났다 — 그 시나리오는
   **일부러** 첫 편집을 되돌린다. 시임이 제 잣대의 오용을 잡은 셈이라 그대로 남기고 뗐다.
3. **불변식 (d)의 쓰기측 계약을 지나지 않았다.** 기존 거부 시나리오는 읽기에서 먼저 막혀
   `persistState`의 덮어쓰기 가드까지 가지 않았다. `afterStateRead` 손잡이를 더해 **읽기
   성공 뒤** 저장소가 더 새 포맷으로 바뀌는 순서를 세웠다(더 새 버전이 같은
   `browser.storage`에 쓰면 실제로 일어난다). 이제 D5가 남긴 둘 중 쓰기측도 실행된다.
4. **`fullReset` 주석이 없어진 큐를 가리키고 금지어를 썼다.** `단일 writer 큐를 지나` →
   CONTEXT.md의 `Writer Lane` `_Avoid_: 큐 (명령 실행자의 것과 혼동)`. 그 큐는 이 diff가
   지웠다. 레인과 증표로 다시 썼다.
5. **"이 파일에서 `lane.run(`을 찾으면 전부 나온다"가 거짓이었다.** 다섯 자리 중 넷이
   `void lane` / 줄바꿈 / `.run(`으로 갈라져 grep이 하나만 찾았다. 직접 호출 셋이 공유하는
   `runCommand` 진입점을 뽑아 획득 자리를 셋으로 줄이고 전부 붙여 썼다 — 중복 셋도 함께
   사라졌다.
6. **`증표`가 용어 사전에 없었다.** `Held`(타입)·`증표`(주석)·`브랜드 토큰`(ADR)로 셋이었다.
   CONTEXT.md에 `증표` 항목을 세워 묶었다. 타입 이름 `Held`는 spec D3의 스케치가 정한
   것이라 그대로 둔다.

**안 고침 — 판단**

- **옮긴 단언 대응표가 네 곳에 있다**(티켓·`executor.test.ts`·`stateStore.test.ts`·S3 인라인).

  바꾸지 않고 용어 사전으로 묶었다(위 6).

로드 경로에 0바이트를 더한다. `wide-ui-redesign`이 남긴 팝업 무게 문제이고, 이 슬러그의
범위(경합 결함 셋)가 아니므로 여기서 고치지 않는다.


### structure 게이트 r1 처분 (2026-07-30)

`ok:true` / needs-attention / **high 1건**. `reviewedSha` `ffff03b`, `headMovedDuringReview: false`.
전문과 트리아지 근거는 `docs/reviews/scope-race-hardening/decisions.md`의 `### structure r1`.

**게이트가 옳았고, 내가 세운 타입 강제가 한 줄로 뚫렸다.** 재현:

```ts
const escaped: Held = await createWriterLane().run(async (held) => held);
await persistState(escaped, createDefaultState());   // 레인 밖 쓰기, bun run check → exit 0
```

`run<T>`의 `T`가 `Held`로 추론되는 것을 막는 것이 없었다. 저널에 "이 블록이 green인 동안에는
레인 밖에서 권위 상태를 쓸 방법이 없다"고 적어 둔 문장이 **거짓이었다**. 함께 세운 구조 가드도
정적 import만 훑어, 렌더러가 이미 쓰고 있는 동적 `import()`로 우회됐다.

**고친 방식 — 두 기제, 서로 다른 구멍**

| 구멍 | 막는 것 | 왜 다른 하나로는 안 되는가 |
|---|---|---|
| 증표 탈출 · 지연 콜백이 붙잡아 둠 | 증표가 `assertLive`를 들고 오고 쓰기 전에 확인 | 산출물 게이트는 서비스워커 **안**의 오용을 못 본다 |
| 화면이 두 번째 레인을 세움 | `scripts/writer-lane-gate.mjs` (빌드 산출물) | 렌더러가 만든 레인의 증표는 렌더러 컨텍스트에서 **살아 있다** |

검사기를 모듈에서 따로 내보내지 않고 **증표가 들고 오게** 한 것이 이 설계의 핵이다. 값으로
내보내면 `platform`의 쓰기 함수가 그것을 import해야 하고, 그러면 화면 번들이 레인 모듈에 —
따라서 `createWriterLane`에 — 닿아 산출물 게이트가 무의미해진다. 증표가 검사기를 들고 오면
쓰기 함수는 타입만 import하면 되고(지워진다) 화면은 레인 모듈을 아예 만나지 않는다.

**산출물 게이트를 고른 이유.** 리뷰의 권고는 "AST/번들러 그래프"였다. TypeScript 7의 Node API에는
파서가 없다(`ts.preProcessFile`·`createSourceFile` 모두 없음). vite의 전이 의존인
`es-module-lexer`·`oxc-parser`가 node_modules에 있지만, 전이 의존에 기대면 vite 업그레이드가
조용히 가드를 무력화한다. 산출물을 읽으면 그 약점이 없고 오히려 더 강하다 — 정적·동적 import·
재수출·별칭·트리셰이킹을 **전부 지나온 뒤**의 사실이기 때문이다. `bundle-gate.mjs`라는 선례도
이미 있다. 표지 문자열의 유무로 판정하고, **서비스워커 번들에 표지가 있는지도 함께 본다** —
그 양성 대조가 없으면 표지가 사라진 상태와 경계가 지켜진 상태가 구분되지 않아 가드는 늘 통과한다.
(실제로 옛 빌드로 돌렸을 때 이 대조가 먼저 잡았다.)

**옛 vitest 가드는 삭제했다.** 같은 성질을 보장하는 기계를 둘 두지 않는다 — 이 티켓이 실행자
tail 체인에 적용한 그 원칙이다.

**남는 한계 (숨기지 않는다).** `as unknown as Held`로 이중 캐스트하며 `assertLive`를 스텁으로
지어내면 두 기제 모두 통과한다. 캐스트 둘과 가짜 검사기를 같은 식에 쓰는 것은 어떤 리팩터링에서도
우연히 나오지 않는 의도적 행위이고, 화면이 **유효한** 증표를 얻는 경로는 산출물 게이트가 막는다.
ADR 0016과 타입 강제 블록 주석에 함께 적었다.

**변이 확인 (전부 red)**: 화면에서 `createWriterLane()` 호출 → 산출물 게이트가 새는 청크
(`global-TJ0qq5Rt.js`)를 짚어 FAIL / 탈출 한 줄 → `TS2739` / 옛 빌드로 게이트 → 양성 대조가 FAIL.


### 시임 재설계 — 쓰기 문 (2026-07-30)

structure r1 픽스를 스스로 적대적으로 공격했고(두 라운드, 렌즈 8개) **두 라운드 모두 실제
결함을 냈다.** 둘 다 릴리스 r3의 R-2를 되살렸고, 둘 다 내가 저널에 적어 둔 문장을 거짓으로
만들었다. 그 기록을 남긴다 — 같은 실수의 모양이 두 번 반복됐다는 것이 이 티켓의 가장 유용한
산출물이다.

**1차 (허가를 콜러에게 넘기던 형태).** 실측:

```ts
await lane.run(async (held) => Promise.all([
  executor.execute(held, { type: 'set-paused', paused: true }),
  executor.execute(held, { type: 'set-badge-visible', visible: false }),
]));
// 두 호출 모두 성공 보고 · 저장소에는 뒤 전이만 — 앞 전이가 조용히 사라진다
```

레인이 직렬화하는 것은 **작업**이지 한 작업 안의 read-modify-write가 아니다. 그리고 D4가
걷어낸 실행자 tail 체인이 **정확히 이 모양을 막고 있었다** — D4의 "같은 성질을 레인이
보장한다"는 주장은 획득 안 fan-out 앞에서 거짓이었다.

**2차 (허가를 서비스에 가두었다고 믿은 형태).** `state-writer.ts`에 "허가가 존재하는 곳은 이
모듈의 `lane.run` 콜백 안뿐"이라 적었는데, 허가는 여전히 내보낸 dep 인터페이스의 파라미터였다
(`BackgroundDeps.persistState`, `BackgroundDeps.commitMigration`, `ExecutorDeps.save`).
컴포지션 루트가 그 슬롯에 넣는 래퍼는 작업 도중 살아 있는 허가를 쥔다. 실측:

```ts
persistState: async (permit, state) => {
  await Promise.all([persistState(permit, state), commitMigration(permit)]);
},
// → 명령이 보고한 값: paused=true / 저장소: paused=false
//   팝업은 {ok:true}와 새 상태를 받아 그리는데 저장소는 옛 값 — 보이는 데이터 손실
```

**두 번이 가르쳐 준 규칙**: 레인 작업 안에서 불리는 **주입된 dep은 그 자체로 fan-out 자리다.**
능력은 허가라는 물건이 아니라 "작업 안에서 불린다"는 사실이므로, 허가를 시그니처에서 빼도
슬롯이 남으면 닫히지 않는다.

**최종 형태.** 문의 구현이 저장소 어댑터를 **직수입한다**(`platform/state-writer.ts`).
그래서 허가가 주입 경계를 하나도 넘지 않고, "한 획득 안에서 병행 쓰기를 띄우지 않는다"를
지켜야 하는 자리가 정말로 그 파일 하나가 된다. `runtime/executor.ts`는 삭제했다 — 별 모듈로
남기면 `ExecutorDeps.save`가 또 하나의 슬롯이 된다. 컴포지션 루트는 `StateWriter` 인스턴스를
주입받고, 그 계약에는 허가가 없다.

| 구멍 | 막는 기제 | 변이 확인 |
|---|---|---|
| 공개 API fan-out | 매소드마다 자기 레인 작업 | S3 `겹쳐 부른 매소드는 직렬화된다` |
| 허가 반환값 탈출 | 조건부 반환형 | `TS2739` |
| 붙잡아 둔 허가·지연 콜백 | 진입 시점 + **쓰기 직전** 재검사 | S3 3건 |
| 검사기 교체 | 허가 동결 | S3 1건 (얼리지 않으면 캐스트 0회로 뚫린다 — 실측) |
| 허가가 모듈 경계를 넘음 | 게이트: 허가를 이름 부를 수 있는 파일 못 박기 | dep 시그니처에 되살림 → FAIL |
| 다른 컨텍스트가 레인을 세움 | 게이트: 레인 생성 1곳 + 워커 도달 밖 표지 없음 | content script 2종 → FAIL |

**게이트를 다시 만든 이유.** 첫 판은 화면 표면을 `*.html`로 **열거**했고, content script는
HTML을 만들지 않아 그대로 지나갔다(실증됨). 열거는 언제나 불완전하므로 질문을 뒤집었다 —
"서비스워커에서 도달하는 파일 밖에 레인이 있으면 실패". 옵션 페이지·devtools가 생겨도 자동으로
덮인다. 워커 쪽에 표지가 **있는지도** 함께 본다(그 대조가 없으면 게이트는 늘 통과한다 — 실제로
옛 빌드로 돌렸을 때 이 대조가 먼저 잡았다).
