# 03 — 클라우드 삭제를 서비스워커로, 백업 변이 요청은 문 하나로

**What to build:** 클라우드 백업 삭제가 자동 Backup과 겹쳐도 결과가 정합하다. 지웠다고 보고되면
정말 지워졌고, 잔재가 남으면 남은 개수를 그대로 보고받는다. 지금은 클라우드 삭제만 화면에서
직접 실행되어 **백업 저장소의 writer가 두 실행 컨텍스트에 서 있다** — 서비스워커의 자동 Backup과
화면의 삭제가 서로를 모른 채 같은 네임스페이스를 고친다. 이 티켓이 릴리스 r3의 R-3 중 남은
절반을 닫고, "서비스워커가 유일한 writer"를 규약이 아니라 배선의 사실로 만든다.

두 요청(스냅샷 한 행 삭제, 클라우드 삭제)을 **문 하나**로 합치고 op 판별 유니온으로 가른다.
문을 하나로 두는 목적은 세 번째 변이를 더할 때 **가장 쉬운 길이 유니온에 가지를 추가하는 것**이
되게 하는 데 있다 — 문이 여럿이면 가장 쉬운 길은 "화면에서 그냥 쓰기"이고, 그게 이번 결함이었다.
설계는 `.scratch/scope-race-hardening/spec.md`의 D6에 있다.

**Blocked by:** 02 — 백업 네임스페이스 쓰기를 레인 안으로.

**Status:** ready-for-agent

- [ ] 클라우드 백업 삭제가 화면에서 직접 실행되지 않는다. 화면은 서비스워커에 요청만 보낸다.
- [ ] 렌더러가 시작하는 백업 변이가 **하나의 요청 문**으로 들어오고, 무슨 동작인지는 판별
      유니온의 가지가 정한다. 스냅샷 한 행 삭제와 클라우드 삭제가 같은 문을 쓴다.
- [ ] 클라우드 삭제도 Writer Lane을 지난다 — 자동 Backup과 겹쳐도 서로의 결과를 덮지 않는다.
- [ ] 잔여 개수 보고가 화면까지 그대로 도착한다. 지우지 못한 잔재를 성공으로 접지 않는다.
- [ ] 전이 명령과 채널을 가르는 기존 결정은 유지된다 — 백업 변이는 권위 상태를 바꾸지 않고
      결과 형태도 다르다.
- [ ] 백업 패널 컴포넌트의 prop 시그니처가 바뀌지 않는다. 바뀌는 것은 기본값이 요청 호출이
      된다는 것뿐이라, 테스트가 대역을 주입하는 방식이 그대로 성립한다.
- [ ] 읽기는 화면에 남는다 — 스냅샷 목록 · 클라우드 잔존 여부 · 스냅샷 본문 로드. 이 티켓은
      읽기 경로를 서비스워커로 옮기지 않는다.
- [ ] 부트스트랩의 중단 재진입 테스트가 **삭제가 아니라 S3로 이동**된다. 지금 그 테스트는
      매니페스트를 아예 만지지 않는 삭제 대역을 써서 중단 깊이 계산만 증명한다 — S3에서는
      진짜 어댑터를 쓴다. 티켓 저널에 옮긴 단언을 행 단위로 대응시켜 적는다.
- [ ] S3가 이 티켓 범위에서 확인하는 조합: 클라우드 삭제 ↔ 자동 Backup, 클라우드 삭제 ↔
      스냅샷 삭제.
- [ ] 손상된 스냅샷도 삭제할 수 있다 — 복원이 막힌 행을 치울 길은 그것뿐이다.
- [ ] 전 게이트 green — 타입 검사 · 단위 · 빌드 · 번들 · 스모크.
