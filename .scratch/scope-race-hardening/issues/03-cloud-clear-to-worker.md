# 03 — 클라우드 삭제를 서비스워커로, 백업 변이 요청은 문 하나로

**What to build:** 클라우드 백업 삭제가 자동 Backup과 겹쳐도 결과가 정합하다. 지웠다고 보고되면
정말 지워졌고, 잔재가 남으면 남은 개수를 그대로 보고받는다. 지금은 클라우드 삭제만 화면에서
직접 실행되어 **백업 저장소의 writer가 두 실행 컨텍스트에 서 있다** — 서비스워커의 자동 Backup과
화면의 삭제가 서로를 모른 채 같은 네임스페이스를 고친다. 이 티켓이 릴리스 r3의 R-3 중 남은
절반을 닫고, "서비스워커가 유일한 writer"를 규약이 아니라 배선의 사실로 만든다.

두 요청(스냅샷 한 행 삭제, 클라우드 삭제)을 **문 하나**로 합치고 op 판별 유니온으로 가른다.
문을 하나로 두는 목적은 세 번째 변이를 더할 때 **가장 쉬운 길이 유니온에 가지를 추가하는 것**이
되게 하는 데 있다 — 문이 여럿이면 가장 쉬운 길은 "화면에서 그냥 쓰기"이고, 그게 이번 결함이었다.
설계는 `.scratch/scope-race-hardening/spec.md`의 D6에 있다.

**Blocked by:** 02 — 백업 네임스페이스 쓰기를 레인 안으로.

**Status:** done

- [x] 클라우드 백업 삭제가 화면에서 직접 실행되지 않는다. 화면은 서비스워커에 요청만 보낸다.
- [x] 렌더러가 시작하는 백업 변이가 **하나의 요청 문**으로 들어오고, 무슨 동작인지는 판별
      유니온의 가지가 정한다. 스냅샷 한 행 삭제와 클라우드 삭제가 같은 문을 쓴다.
- [x] 클라우드 삭제도 Writer Lane을 지난다 — 자동 Backup과 겹쳐도 서로의 결과를 덮지 않는다.
- [x] 잔여 개수 보고가 화면까지 그대로 도착한다. 지우지 못한 잔재를 성공으로 접지 않는다.
- [x] 전이 명령과 채널을 가르는 기존 결정은 유지된다 — 백업 변이는 권위 상태를 바꾸지 않고
      결과 형태도 다르다.
- [x] 백업 패널 컴포넌트의 prop 시그니처가 바뀌지 않는다. 바뀌는 것은 기본값이 요청 호출이
      된다는 것뿐이라, 테스트가 대역을 주입하는 방식이 그대로 성립한다.
- [x] 읽기는 화면에 남는다 — 스냅샷 목록 · 클라우드 잔존 여부 · 스냅샷 본문 로드. 이 티켓은
      읽기 경로를 서비스워커로 옮기지 않는다.
- [x] 부트스트랩의 중단 재진입 테스트가 **삭제가 아니라 S3로 이동**된다. 지금 그 테스트는
      매니페스트를 아예 만지지 않는 삭제 대역을 써서 중단 깊이 계산만 증명한다 — S3에서는
      진짜 어댑터를 쓴다. 티켓 저널에 옮긴 단언을 행 단위로 대응시켜 적는다.
- [x] S3가 이 티켓 범위에서 확인하는 조합: 클라우드 삭제 ↔ 자동 Backup, 클라우드 삭제 ↔
      스냅샷 삭제.
- [x] 손상된 스냅샷도 삭제할 수 있다 — 복원이 막힌 행을 치울 길은 그것뿐이다.

## Comments

### 구현 저널 (2026-07-30)

**릴리스 r3의 R-3이 여기서 닫힌다.** 클라우드 삭제가 화면에서 서비스워커로 옮겨 오면서
`bk:` writer가 한 실행 컨텍스트로 모였다. "서비스워커가 유일한 writer"가 규약이 아니라
**타입과 배선의 사실**이 됐다 — `clearCloudBackups`가 허가를 요구하므로 화면은 그것을 부를
방법이 없다. 프로브로 확인했다: `src/app`에서 `clearCloudBackups()`를 부르면 컴파일 오류다.

**문 하나 · 판별 유니온** (D6). 두 요청이 하나로 합쳐졌다.

```
requestSnapshotDelete(id, target)          →  requestBackupMutation(mutation)
onSnapshotDeleteRequest(handler)           →  onBackupMutation(handler)
StateWriter.deleteSnapshot(id, target)     →  StateWriter.mutateBackup(mutation)
```

`BackupMutation`은 `{ op: 'delete-snapshot' | 'clear-cloud' }` 유니온이고 `core/state-writer.ts`에
산다. 세 번째 가지를 넣는 것이 **가장 쉬운 길**이 되게 하려는 것이 목적이라, `switch`에
`mutation satisfies never`를 달아 빠진 가지가 **이름과 함께** 컴파일 오류가 되게 했다. 확인:
`{ op: 'prune-orphans' }`를 더하면 `TS2345`가 그 op을 지목한다.

**패널 prop 시그니처는 바뀌지 않았다** (수용 기준). `clearCloud?: () => Promise<…>`와
`deleteSnapshot?: (entry, target) => Promise<…>`가 그대로다 — 바뀐 것은 기본값이 요청 호출이
됐다는 것뿐이라 테스트가 대역을 주입하는 방식이 성립한다. 결과 타입은 세 이름이 하나를
가리키게 정리했다: `BackupMutationResult`(정본) ← `DeleteSnapshotResult`·`ClearCloudResult`.

**읽기는 화면에 남았다** (D7) — 목록·클라우드 잔존 여부·본문 로드. 이 티켓은 읽기 경로를
옮기지 않는다.

**옮긴 단언 — 원래 위치와 행 단위 대응.** 이 티켓이 옮길 예정이던 것은 **티켓 02에서 이미
옮겨졌다**: `runtime/background-bootstrap.test.ts:415` `겹친 중단은 재진입 안전하다` →
S3 `겹쳐 도착한 두 삭제가 둘 다 완료되고 서로의 결과를 지우지 않는다`. 티켓 02가 그 테스트가
겨누던 중단 깊이 카운터를 걷어냈으므로 그때 함께 옮기는 것이 맞았다. 근거는 이동 자리에
주석으로 남아 있다(`service-worker.integration.test.ts`의 티켓 02 절).

**S3 조합 둘 추가** — 클라우드 삭제 ↔ 자동 Backup, 클라우드 삭제 ↔ 스냅샷 삭제. 둘 다 **같은
구역(sync)**을 다투는 것이 요점이라 `syncBackup` 기본값(true)을 쓰고 `seedSync`로 클라우드에
백업을 깔았다. 단언은 목록→데이터(`manifestBacked`)와 데이터→목록(`orphanChunks`) 양방향이다 —
한 방향만 보면 "하나가 다른 하나의 항목을 지우고 청크만 남긴" 손실이 보이지 않는다.
변이 확인: 레인 직렬화를 제거하면 둘 다 red.

**손상 스냅샷 삭제**를 어댑터 시임에 못 박았다 — `chunkCount`가 2인데 청크가 하나뿐인 행도
항목과 잔해가 함께 사라진다. 계획이 청크를 `bk:<id>:` 접두 전체에서 모으기 때문이다. 복원이
막힌 행을 치울 길은 삭제뿐이므로 이 성질이 없으면 사용자가 그 행을 영구히 안고 산다.

### `/code-review` 처분 (2026-07-30)

고정점 `5e29529`. 두 축이 낸 지적 대부분을 수용했다.

1. **게이트 주석이 "티켓 03이 옮긴다"고 적힌 채였다** — 이것이 티켓 03이다. ADR 0016이
   "주석 규약을 쓰지 않는 이유"로 든 바로 그 실패 모양이라 즉시 고쳤다. 두 리뷰가 독립적으로
   같은 것을 짚었다.
2. **`ClearCloudResult`가 세 번째 독립 선언이었다** — `DeleteSnapshotResult`는 계약 층 별칭으로
   바꿨는데 이쪽을 빼먹었다. 같은 커밋에서 "두 곳에 같은 모양을 따로 적어 두면 곧 어긋난다"고
   적어 놓고 어긴 셈이다. 둘 다 `BackupMutationResult`의 별칭으로 정리했다.
3. **`clearCloud`가 이제 던질 수 있다** — 화면에서 직접 지울 때는 없던 실패 모양이다.
   서비스워커 교체 중 `sendMessage`가 "Could not establish connection"으로 던지면 패널의
   `void` 호출에서 삼켜져, 확인 버튼만 되돌아오고 설명이 없다. 두 곳을 고쳤다:
   `requestBackupMutation`이 결과 객체로 바꾸고(채널 양 끝이 같은 약속을 하게), 패널도
   `settledMutation`으로 주입된 대역의 거부까지 배너에 올린다.
4. **죽은 `else` 가지** — 클라우드↔백업 시나리오는 레인이 순서를 고정(백업→삭제)하므로 잔재
   갈래에 도달하지 않는다. 검증하는 척하는 가지를 없애고 결정된 값을 그대로 단언했다.
5. `installStorageFake`의 `Kv` 두 positional(서로 바꿔 넣어도 조용하다)을 이름 붙인 객체로,
   패널의 결과 타입 출처를 계약 층으로, 중복된 근거 문단을 정본 한 곳 + 포인터로 정리했다.

**안 고침**
- **`op: 'clear-cloud'`가 계약 층에서 '클라우드'를 쓴다**는 지적. CONTEXT.md의 `_Avoid_`는
  `cloud sync`(외부 서버 동기화 오해)를 가리키고 `clear-cloud`는 그것이 아니며, spec D6이 이
  판별자 이름을 그대로 적어 승인됐다.
- **긴 줄 몇 개**. 전부 한 줄 문서 주석이나 테스트 제목이고, 저장소에 그 폭의 줄이 이미 많다.
  줄 길이 규약이 문서화된 곳이 없어 churn만 남는다.
- **`onBackupMutation`이 `onCommand`의 봉투를 재현한다**(T15-R-2)·**`stateStore.ts`의 Divergent
  Change**(T15-R-6). 둘 다 이월된 항목이고 이 티켓의 범위가 아니다.
