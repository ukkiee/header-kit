# 06 — 겹친 삭제 끝단간 스모크와 N43 포인터 갱신

**What to build:** Writer Lane이 **실제로 배선됐다**는 것이 진짜 서비스워커·진짜 메시지 채널·
진짜 브라우저 저장소를 지나 확인된다.

이 확인이 따로 필요한 이유는 규모가 아니라 배선이다. S3의 인터리빙 소진은 제어형 fake 위에서
돌므로 "레인이 배선됐는가"를 증명하지 못한다 — 새 요청 핸들러를 레인 밖에 달아도 단위는 전부
green이다. 그리고 릴리스 게이트가 두 라운드 연속으로 "스모크가 동시성을 비껴간다"를 지적했으므로,
스모크에 동시성을 보는 시나리오가 하나도 없는 상태로 릴리스에 들어가면 같은 지적을 다시 받는다.

**Blocked by:** 03 — 클라우드 삭제를 서비스워커로, 백업 변이 요청은 문 하나로.

**동시성을 UI 클릭으로 만들 수 없다.** 패널은 확인 중인 행·동작을 한 번에 하나만 허용하므로

변이 채널(`headerkit:backup-mutation`)로 두 요청을 보내되 **어느 것도 await하지 않고 둘 다
출발시킨 뒤 함께 기다린다**. 이 파일에 선례가 있다 — `E4`가 같은 방식으로 명령 봉투를 직접 보낸다.
메시지 `type` 문자열 하드코딩은 결합이지만 **닫힌 결합**이다: 상수가 드리프트하면 구독자가
응답하지 않아 삭제가 일어나지 않고 단언이 큰 소리로 깨진다(`BACKUP_MUTATION_MESSAGE`는 export되지
않으므로 import할 방법도 없다).

#### `/code-review` — 발견 10건, 검증 4건 (확정 1 · 반박 3)

**확정 (Standards S-2와 Spec SPEC-01이 독립 수렴).** 유지 행의 "손상 아님" 단언 둘이 **경합 전에
렌더된 DOM**을 읽고 있었다. 삭제를 원시 채널로 보냈으므로 패널의 목록 effect
(`[open, loadSnapshots, target]` — 셋 다 이 구간에서 고정)가 다시 돌지 않아, 그 값들은 시드가 참으로
만들어 둔 것이지 경합 결과가 아니었다. **리뷰에 최우선으로 지시한 함정을 내가 또 밟았다** — 복원
단언에서 한 번 밟고 고쳤는데 같은 종류가 옆에 하나 더 있었다.
고침: 경합 **뒤에** 목록을 다시 읽어 유지 행이 보이는지 + **지운 둘이 사용자가 보는 목록에서도
사라졌는지**를 본다. 로케일에 걸린 `/corrupt/i` 부정 검사는 지웠다(ko 카탈로그에서는 원리적으로
깨질 수 없다) — 손상 행은 복원 버튼 **대신** 표식이 그려지므로 복원 성립이 더 강한 비손상 증거다.

**반박 3건 — 다시 열지 말 것.**
