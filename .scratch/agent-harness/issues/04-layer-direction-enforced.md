# 04 — 레이어 방향이 강제된다

**What to build:** 상향 import를 쓰면 즉시 실패한다. 지금 **레이어 방향**은 지난 기능의 리뷰 산출물에만 적혀 있고 강제하는 것이 하나도 없다 — 실제로 위반이 이미 하나 있는데 아무도 몰랐던 것이 아니라 알 방법이 없었다.

`oxlint`가 들어와 린트·접근성 이전의 일반 규칙·레이어 방향·순환 import를 한 실행으로 본다. `tsc --noEmit`은 **그대로 둔다** — 대체는 두 진단 집합이 같다는 측정되지 않은 주장을 전제하고, 틀렸을 때 생기는 것이 정확히 검사하지 않는 초록 게이트다.

레이어 방향은 `overrides` + `no-restricted-imports`로 표현한다(`oxlint`에는 `import/no-restricted-paths`가 없다). 그 방식의 약점은 21쌍 중 한 줄이 빠져도 설정이 조용히 통과한다는 것이고, **그것을 닫는 것은 설정이 아니라 픽스처**다.

유일한 실측 위반인 서비스워커 통합 테스트를 `entrypoints`로 옮긴다. 그 테스트가 재는 것이 실제로 배경 컴포지션 루트의 동작이므로 자리가 뜻과 맞는다. 테스트를 게이트 범위 밖으로 빼지 않는다 — 그러면 테스트가 레이어를 뚫는 것을 영구히 허용하게 된다.

**Blocked by:** 01

**Status:** ready-for-agent

- [ ] **가장 먼저 잰다:** `oxlint`의 `overrides.files` 패턴이 설정 파일 위치 기준인지 실행 cwd 기준인지. 픽스처 트리가 성립하려면 후자여야 하고, 아니면 설정을 픽스처 트리에 복사해 넣는 형태로 바꾼다. **가정하지 않는다**
- [ ] `lint` 게이트가 등록되고 표에 행이 선다. `check`(tsc)는 그대로 남는다
- [ ] 일곱 층 각각에 다른 여섯 층을 전부 import하는 파일을 둔 픽스처 트리에서 `oxlint`를 **한 번** 돌려, **상향 21쌍이 전부 보고되고 하향 쌍은 하나도 보고되지 않는다**. `overrides`에서 한 줄이 빠지면 그 쌍이 출력에 없어 테스트가 빨강이다
- [ ] 설정 파일을 읽어 쌍을 세는 방식은 쓰지 않는다 — 그것은 표가 완전한지만 보고 표가 실제로 거절하는지는 보지 못한다
- [ ] `import/no-cycle`이 켜지고, 순환을 만든 픽스처가 FAIL을 낸다
- [ ] 서비스워커 통합 테스트가 `entrypoints`로 옮겨졌고, 그 뒤 레이어 게이트가 프로덕션 코드와 테스트 전부에 대해 초록이다
- [ ] `*.test.ts`·`*.stories.tsx`를 레이어 검사에서 예외로 두지 않는다
- [ ] 실측으로 나온 기존 위반(미사용 타입 import 다섯 곳, 테스트 두 곳의 불필요한 spread)이 고쳐졌다. 베이스라인을 만들어 미루지 않는다 — 열 건이라 그냥 고칠 수 있다
- [ ] `oxlint`의 검사 범위에 `scripts/`가 포함되고, **타입 없이 잡히는 것만** 잡는다는 경계가 표에 적혀 있다. 첫 실행의 기존 위반은 베이스라인으로 기록되며 늘어날 수 없다
- [ ] `src/`에 await되지 않은 프로미스를 둔 픽스처가 **FAIL을 낸다** — 규칙이 목록에 있다는 것과 규칙이 실제로 도는 것은 다르고, type-aware가 켜지지 않으면 이 규칙은 조용히 아무것도 하지 않는다
- [ ] 이 티켓은 jsx-a11y를 켜지 않는다. 그것은 포맷 적용 뒤에 오는 06의 일이다
- [ ] `bun run check`와 `bun run test`가 여전히 초록이다
