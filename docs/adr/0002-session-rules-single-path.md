# 네트워크 규칙은 session rules 단일 경로로 관리한다

프로필 저장소(`storage.local`)를 단일 진실 원천으로 삼고, 변경·브라우저 시작 시마다 활성 Profile 전체를 DNR session rules로 전량 재생성한다. Tab Filter의 `tabIds` 조건이 session rule 전용이라 session 경로는 어차피 필수이며, dynamic rules를 병용하면 두 규칙 저장소의 정합성을 상시 맞춰야 하는 반면 unsafe 규칙 quota는 5,000으로 동일해 얻는 것이 없다. 대가로 브라우저 재시작 직후 service worker가 재생성을 마치기 전까지 수백 ms의 규칙 공백을 감수한다.

## 개정 — `tabIds` 근거가 사라졌다, 결론은 유지한다 (ADR 0017, 티켓 10)

위 결정의 첫 근거였던 **"Tab Filter의 `tabIds` 조건이 session rule 전용이라 session 경로는 어차피 필수"가 더 이상 참이 아니다.** ADR 0017이 탭 도메인 조건을 퇴역시키면서 컴파일이 `tabIds`를 아예 방출하지 않게 됐다 — 이제 방출되는 규칙 중 session 경로를 **강제하는** 것은 하나도 없다.

**그래도 session rules 단일 경로를 유지한다.** 남은 근거 둘은 그대로다:

- **정합성 비용**: dynamic을 병용하면 두 규칙 저장소를 상시 맞춰야 하고, 그 대가로 얻는 quota는 없다(unsafe 5,000으로 동일).
- **끄면 흔적을 남기지 않는다** (ADR 0001): session rules는 브라우저 세션이 끝나면 **저절로** 사라진다. dynamic rules는 브라우저를 다시 켜도 살아남으므로, "끈다"가 **우리 코드가 지워 줘야만** 성립하는 일이 된다 — 서비스 워커가 그 일을 못 하고 죽은 창(업데이트 중단·크래시)에서 옛 규칙이 계속 걸린다. 제거 자체는 확장을 지우면 브라우저가 함께 하지만, 이 제품이 약속한 것은 삭제가 아니라 **끈 동안 안 걸리는 것**이고 그 실패 모드가 session 쪽에서 유계다.

**이 개정을 남기는 이유**: 근거가 증발한 것을 적어 두지 않으면 다음 사람이 "탭 조건도 없는데 왜 session인가"를 묻고, 낡은 전제 위에서 dynamic rules로 "단순화"한다. 지금 유지하는 이유는 위 둘이지 `tabIds`가 아니다.

**함께 사라진 것**: 만료 알람과 탭 감시 서브시스템, 그리고 `alarms`·`tabs` 권한. 컴파일 입력에서 열린 탭 목록과 현재 시각이 빠져 **같은 상태에 같은 결과**가 된다 — 재조정이 언제 돌아도 같은 규칙 집합이 나온다.
